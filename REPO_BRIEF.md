# ScriptureForgeAI Repo Brief

## Purpose

ScriptureForgeAI is a multi-tenant Bible study platform with authenticated workspaces, encrypted journals, AI-assisted study generation, live study rooms, Zoom integration, a Rust scripture engine, Terraform deployment skeletons, and production-readiness evidence tooling.

## Stack

- Backend: Go `1.24.3` toolchain, `net/http`, `pgx`, Redis, Gorilla WebSocket, OpenTelemetry.
- Web: Next.js `16`, React `19`, TypeScript, Zustand.
- Mobile: Expo/React Native, TypeScript, Zustand, `react-native-quick-crypto`.
- Worker/service: Rust `2021`, Tokio, Tonic gRPC, vendored `protoc` via `protoc-bin-vendored`.
- Data/infrastructure: PostgreSQL with pgvector, Redis, Terraform AWS/EKS/RDS/Redis skeleton, Kubernetes workload manifests generated by Terraform.

## Commands

Use the parent RTK rule when available: prefix external commands with `rtk`. If `rtk` is unavailable in the local shell, report that as an environment blocker and use the safest local equivalent only when needed.
For a fresh Windows shell that has not picked up user PATH changes yet, run `tools\use-project-path.cmd` from the repo root to verify PATH, or prefix a command with `tools\use-project-path.cmd <command>`. The PowerShell equivalent is `tools/use-project-path.ps1 <command>` with an allowed execution policy.
For staging evidence collection, use `tools\use-project-path.cmd --strict-staging` or `powershell -ExecutionPolicy Bypass -File tools\use-project-path.ps1 -StrictStaging`.

- PATH/tool readiness: `node tools/verify-project-path.mjs`
- Staging evidence PATH readiness: `node tools/verify-project-path.mjs --strict-staging`
  - Strict staging mode requires staging CLIs to resolve and pass version checks; broken shims are blockers just like missing tools.
- Persist Windows user PATH for fresh shells/GUI tools: `powershell -NoProfile -ExecutionPolicy Bypass -File tools\install-project-path.ps1`
- Backend tests: `go test ./...`
- Backend vet: `go vet ./...`
- Docker-backed local tenant/RLS proof: `node tools/run-rls-db-integration-docker.mjs`
- Web: `cd web && npm run smoke && npm run typecheck && npm run build`
- Mobile: `cd mobile && npm run smoke && npm run build:check`
- Rust: `cd services/scripture-engine && cargo test --locked`
- Terraform local validation: `cd build/terraform && terraform fmt -check -recursive && terraform init -backend=false && terraform validate`
- Serena/Obsidian drift: `node tools/validate-serena-obsidian.mjs`

## Data, Auth, And External Service Notes

- Tenant isolation depends on Postgres RLS plus `auth.SetTenantContext(ctx, tx, orgID)` for tenant-scoped handler transactions.
- Journal entries must remain ciphertext-only on the backend; clients must not send plaintext or passphrases.
- Auth uses short-lived access tokens, opaque refresh tokens, tenant-bound organization IDs, and privileged-role MFA flows.
- Live rooms use authenticated HTTP/WebSocket routes under `/api/v1/rooms/*`, Redis-backed sequencing, room membership checks, and allowed-origin validation.
- AI and Zoom paths should fail closed or degrade with typed errors; production evidence requires staging probes, not local-only tests.

## Do-Not-Touch / Risk Zones

- Do not commit secrets, `.env*` files, Terraform state, local evidence manifests, or generated caches.
- Avoid editing generated protobuf output unless regenerating intentionally from `proto/scripture.proto`.
- Treat `artifacts/`, `.tools/`, `.gocache/`, `.npm-cache/`, `node_modules/`, `.next/`, `target/`, `.terraform/`, and `*.tsbuildinfo` as local/generated.
- Do not weaken production-readiness wording: if proof is local-only or staging evidence is missing, keep that boundary explicit.
- Do not change app behavior during Serena/Obsidian setup work unless explicitly requested.
